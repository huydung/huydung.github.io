How to use this guide

Work top to bottom. Each phase has a checklist (tick as you go) and one or more ready-to-use prompts — copy the prompt, paste it into your AI, and replace anything marked [LIKE THIS] with your own game's details. You stay the designer and director; the AI executes.

You direct, AI executesThe idea and the judgment are yours. The AI is a thinking partner and a coder, not a replacement for either.
Plan first, then build smallLock the design before any code. Build in small, testable steps — never one giant request.
Prototype scope onlyYou are proving the core mechanic is fun. Resist polishing, feature-creep, and chasing tiny bugs.
Keep docs leanA Concept Card and a 2-page GDD beat a 30-page design bible. The doc grows only as the game proves itself.

0Set up your tools

One-time setup. You need a place to store code, a way to read it, and an AI coding agent.

  • Create a GitHub account and a new public repository. This stores every step so you can compare, roll back, and host the game for free later.
  • Install GitHub Desktop and clone the repo to your machine. A friendly UI for commits — you won't need the command line.
  • Install Visual Studio Code with a Markdown preview extension. To read the code the AI writes and make tiny tweaks yourself — faster than asking the AI.
  • Pick and install ONE AI coding agent (desktop app). See the comparison below. The workflow is nearly identical across all three.
  • Pick ONE chat AI for design discussion (can be the same provider). Used for brainstorming and writing the design docs before any code.

Model selection — important

For brainstorming & design (Phases 1–3), use a mid / creative model (e.g. Claude Sonnet, Gemini Flash, ChatGPT "medium" reasoning) — top models over-optimize for logic and under-deliver on creativity.

For the technical plan and coding (Phases 4–6), start with the mid-level model too — for a game prototype it works fine about 90% of the time. Only switch up to the strongest model (Opus, Gemini Pro, ChatGPT high reasoning) when you genuinely can't get the result you want.

1Find the idea

Use the chat AI as a thinking partner. Make it ask you questions — the best idea still comes from you. Pick whichever prompt matches your situation: an open brainstorm, or one anchored to a specific theme.

  • Use a creative (mid-tier) model, in English if you can. Saves tokens and improves quality.
  • State who the audience is — both prompts ask for it, because "impressive for non-coders" and "impressive for students" lead to very different ideas.
  • Make the AI ask you clarifying questions before it proposes anything.
  • Demand a comparison table of 10+ ideas scored on clear criteria, so you can choose objectively.
  • Pick ONE idea. Don't expand two. Scope discipline starts here.

Version A — open brainstorm (no fixed theme)

PROMPT · Brainstorm — open 
I'm running a workshop teaching people how to prototype games with AI. The audience is [DESCRIBE AUDIENCE — e.g. "game studio staff who are NOT coders", "students new to game dev"]. The demo game must impress them and be easy to follow.

I need ONE creative, demo-worthy game idea. Let's brainstorm together — ask me clarifying questions first if anything is vague, don't jump straight to answers.

Constraints for the idea:
- Must play well on BOTH desktop and mobile (fun with touch / tap / swipe)
- ONE interesting, reasonably innovative core mechanic — not a clone
- Small enough to prototype in a few hours (a vertical slice, not a full game)

My hobbies / interests to draw from (optional): [FILL IN — e.g. Poker, Pool, Piano, Origami — or delete this line]

When I say "ready", present at least 10 ideas in a TABLE, in an artifact, comparing them on:
Innovativeness | Mobile-first fit | Core mechanic clarity | Prototype feasibility (hours) | Demo appeal for my audience.
Then recommend your top 3 with one line on why each fits an AI-dev demo for this audience.

Version B — themed brainstorm (AI researches the theme first)

PROMPT · Brainstorm — with a theme 
I'm running a workshop teaching people how to prototype games with AI. The audience is [DESCRIBE AUDIENCE — e.g. "game studio staff who are NOT coders", "students new to game dev"]. The demo game must impress them and be easy to follow.

I want the demo game built around this theme: [STATE YOUR THEME — e.g. "Dragon Mania Legends", "Vietnamese folk tales", "office life at a game studio"].

First, RESEARCH the theme so the ideas feel authentic:
- Look up the theme's signature elements, characters, mechanics, tone, and visual identity.
- Summarize back to me, in a short list, the 5–8 most distinctive things about it that a game could build on.

Then brainstorm with me. Ask clarifying questions if needed. Each idea must:
- Stay true to the theme's identity
- Play well on BOTH desktop and mobile (fun with touch / tap / swipe)
- Have ONE interesting, reasonably innovative core mechanic — not a clone
- Be small enough to prototype in a few hours (a vertical slice)

When I say "ready", present at least 10 theme-based ideas in a TABLE, in an artifact, comparing them on:
Innovativeness | Mobile-first fit | Core mechanic clarity | Prototype feasibility (hours) | Theme authenticity | Demo appeal for my audience.
Then recommend your top 3 with one line each on why they fit both the theme and an AI-dev demo for this audience.

2Lock the design — the Concept Card

Before any GDD, nail the mechanic on a single, focused page (up to ~1000 words) and get a quick visual mockup of the main screen. This is the biggest scope-saver. Discuss in chat until the loop feels fun on paper.

  • Keep it to ~1000 words max. If it can't fit, the prototype is too big.
  • The core mechanic is one sentence you can say out loud. If you can't, keep refining.
  • Get a visual mockup of the main gameplay screen — a labelled wireframe shows layout problems before any code exists.
  • Define the vertical slice — the smallest thing that proves the mechanic is fun.
  • Write the non-goals. What you won't build matters as much as what you will.
  • Resolve ambiguity in chat first, then let the AI write the card.
PROMPT · Write the Concept Card (+ mockup) 
Great — let's lock the design. We are NOT writing a full GDD yet.

Produce a CONCEPT CARD — concise, up to ~1000 words max — for: [GAME NAME / chosen idea]

Use exactly these sections, concrete and specific:
1. One-line pitch (≤ 25 words)
2. Core mechanic (the ONE thing that makes it fun — describe the moment-to-moment interaction in detail)
3. Core loop (a 4–6 step arrow chain, e.g. aim → shoot → pocket → assign → repeat)
4. Win / lose (or "no fail state" — say which, and why)
5. Controls (mobile tap/swipe AND desktop — be explicit for each)
6. What's IN the prototype (the vertical slice — the smallest thing that proves the mechanic is fun)
7. What's OUT / non-goals (everything we are deliberately NOT building yet)

Then add a VISUAL MOCKUP of the main gameplay screen: produce it as a clean labelled wireframe (an inline SVG or a simple HTML/CSS mockup in an artifact) showing the core screen layout — where the play area, the player's controls, the HUD/score, and any key UI elements sit. Keep it schematic, not polished art.

Ask me up to 3 questions if anything is ambiguous BEFORE writing. Keep the whole thing tight enough to fit the scope of a prototype, not a commercial game.
Why a Concept Card, not a GDD yet

Industry practice for prototypes: start with a one-pager and let the doc grow only as the game proves itself. A heavy GDD up front locks in decisions you haven't tested and bloats the AI's context — which is exactly when AI starts to hallucinate and break things.

3Write the Prototype GDD

Now expand the Concept Card into a lean design doc — capped at ~2 pages, pure design, zero technical content. Save it as gdd.md.

  • Markdown, under ~2 pages. .md is clear, concise, token-cheap — the AI's preferred format.
  • Design only. No file names, code, formulas, or configs — all of that belongs in the TDD.
  • Includes explicit Non-Goals / Out-of-Scope.
  • Every rule is implementable by a stranger — no "you know what I mean".
  • Review it in VS Code and fix small things yourself before moving on.
PROMPT · Generate gdd.md 
Now turn the Concept Card into a PROTOTYPE GDD as a Markdown file: gdd.md

Rules:
- This is a PROTOTYPE design doc, not a commercial GDD. Keep it lean — aim for under ~2 pages.
- Pure design only. NO technical content (no file names, no code, no formulas, no configs) — that goes in the TDD.
- Structure: Pitch · Design Pillars (2–4) · Core Mechanic · Core Loop · Rules · Controls (mobile + desktop) · Win/Lose · In-Scope (vertical slice) · Non-Goals.
- Every rule must be unambiguous enough that a coder who never spoke to me could implement it.
- Where a number matters (turn limit, hand size, timing window), state it — but keep it in plain language, not code.

First research what a lightweight prototype GDD should contain, then write gdd.md. Ask me anything unclear before writing.

4Write the TDD — with all the rules baked in

Don't ask for a "technical design document" generically — the AI will give you something bland. Hand it your exact engineering constraints. This prompt already contains all of them. Save the result as tdd.md.

  • Centralized config + zero magic numbers so non-coders can tweak and playtest.
  • Strict separation of concerns (physics / render / rules) — keeps the AI from breaking everything on a refactor.
  • Incremental edits + commit after every turn with conventional messages.
  • Logging, non-coder comments, and a test suite run every turn.
  • Workspace & build health checks before the AI reports success.
PROMPT · Generate tdd.md (rules baked in) 
Put on the Game Architect hat. Create tdd.md (Technical Design Document) for this prototype, based on gdd.md.

Move ALL technical content here: architecture, code conventions, math/formulas, and the full list of tunable configs.

The TDD MUST explicitly encode every one of these requirements — do not paraphrase them away:

ARCHITECTURE & CONFIG
1. Single centralized configuration file. ALL mechanical, physical, and rules-based constants live in one dedicated config file (e.g. src/config.js) so non-coders can tweak and playtest.
2. Zero Magic Numbers. No pixel dimensions, speeds, friction, colors, or turn limits hardcoded in game loop, physics, or render files.
3. Self-documenting config. Every config key has a natural-language comment explaining what it changes and its recommended range.
4. Maximum separation of concerns — decoupled source files. As a model:
   - Physics layer: rigid-body coords, collisions, momentum ONLY. Zero knowledge of rules/turns/score.
   - Render layer: turns physics coordinates into visible entities; animations, HUD, particles.
   - Rules & State engine: evaluates state, turns, win conditions; driven by physics events but physically decoupled.
   (Adapt these layers to MY game's mechanic, but keep the strict decoupling.)

AI WORKING DISCIPLINE
5. Incremental edits only. No massive sweeping rewrites across the codebase. Small, testable changes.
6. Commit after every turn. On completing a request: run a local compile/build check, and if it passes, do a Git commit with a clear conventional message (feat:/fix:/chore:/test:). If the build fails, fix it first.
7. Automated workspace diagnostics. Before reporting done, verify the local dev server is running; if not, start it. Note any sandbox limitation that blocks running the server/tests locally and tell me to run it on my machine instead.
8. Health & compilation check. Confirm the build compiles cleanly with no errors before reporting success.
9. Logging. Add log messages with essential info at all key interactions for easy debugging.
10. Comments for non-coders. Add enough code comments to guide a non-coder on how to modify important behavior.
11. Tests. Write a test suite for all logic-based code and run it every turn. Update tests for each new feature or design change.

Write tdd.md now. Ask me about my game's specific layers/mechanic if you need to before finalizing.
Git discipline — run this once, early

Before the agent writes much code, set up version tracking and the commit habit:

PROMPT · Initialize git + commit habit 
Initialize a git repo and commit all current files in this folder.

From now on, in ALL of our conversations: after each turn, run a build/compile check; if it passes, commit all changes with a clear, concise, conventional message (feat:/fix:/chore:/test:), and push to this repo: [PASTE YOUR GITHUB REPO LINK]

If the build fails, fix it before committing.

5Build plan — 3 milestones

Three milestones, not five — but split them around your game's own mechanic, not a fixed template. The AI proposes the division and explains its reasoning; you sanity-check it. Each milestone ends in something you can actually play or test.

  • Exactly 3 functional milestones, each building on the last.
  • Divided by what THIS game needs — the mechanic drives the split, not a generic "setup / build / polish" template.
  • Every milestone delivers real functionality — "polish" is not a milestone. This is a prototype; milestone 3 is the rules + win/lose + full loop + deploy, not a cosmetic pass.
  • Each milestone has a user-facing test checklist and a copy-paste agent prompt.
  • Sanity-check the plan — have the AI summarize the 3 milestones and its reasoning back to you before building.
PROMPT · Generate plan.md (3 milestones) 
Put on the Tech Lead hat. Create plan.md — a build plan with EXACTLY 3 milestones (not more).

Important: the 3 milestones must be split MEANINGFULLY around THIS game's own mechanic — not a generic template. Read gdd.md and tdd.md, then divide the work into 3 functional layers that each build on the previous one and each end in something I can actually play or test. As a rough guide (adapt to the game):
- Milestone 1 is usually the static foundation: scaffold, centralized config, the scene/board/world laid out correctly, HUD placeholders, clean module boundaries. It runs and looks right; the core interaction isn't live yet.
- Milestone 2 is usually the core mechanic itself — the ONE thing that makes the game fun, working end-to-end (input → simulation/logic → feedback). This is the milestone that proves the idea.
- Milestone 3 is usually the rules, win/lose, and full game loop wrapped around that mechanic, plus a GitHub Pages deploy so it's shareable.
But you decide the actual split based on what this specific game needs — tell me your reasoning for the division before listing the details. Do NOT make milestone 3 a generic "polish" pass; this is a prototype, so every milestone must deliver real functionality.

Each milestone must include:
(a) a short scope paragraph,
(b) a checklist of things to test FROM THE END-USER's perspective,
(c) a single copy-paste prompt for the local AI coding agent — and that prompt must explicitly remind the user to run the test checklist.

Follow tdd.md for all conventions. Write plan.md now.

6Build, milestone by milestone

Switch to your AI coding agent (not chat) — it reads, writes, and runs files directly. One milestone per chat session to keep context clean. Start with the mid-level model; only escalate if you get stuck.

  • New session per milestone. Avoids context overflow and hallucination; easier to search later.
  • Run the milestone prompt (below), then do the test checklist from plan.md yourself.
  • Check the config decoupling: open config.js in VS Code and confirm values actually live there, not hardcoded.
  • Review the git commits after each milestone — you should be able to follow the story.
  • After a milestone, refresh the docs (gdd/tdd/plan), then open a fresh session for the next.
PROMPT · Run a milestone 
We are building [GAME NAME]. Read gdd.md, tdd.md, and plan.md first.

Execute Milestone [1 / 2 / 3] from plan.md, following every convention in tdd.md (centralized config, zero magic numbers, separation of concerns, incremental edits, logging, comments, tests, commit-after-turn).

Work in small testable steps. When done, run the milestone's end-user test checklist from plan.md and report the results.

Reminder: do NOT introduce magic numbers, do NOT make sweeping rewrites, and verify the build compiles before reporting success.
PROMPT · Refresh docs after a milestone 
Milestone [N] is complete and tested. Update gdd.md, tdd.md, and plan.md to reflect what we actually built and any decisions that changed. Commit the doc updates. Then summarize what's left so I can start the next milestone in a fresh session.

7Fix bugs the smart way

Iteration is normal — even human devs never get it right in one shot. Give the AI the right evidence and it fixes fast.

  • Visual bug → attach a screenshot. Words alone rarely convey a layout problem.
  • Logic bug → open DevTools (F12) → Console → paste the full log.
  • Watch the AI "think" — if it's heading the wrong way, stop it early to save time and tokens.
  • Stuck for a while? Start a fresh session and ask it to explain the feature's flow before fixing.
  • Tell it to add debug logs when a bug is hard to pin down.
PROMPT · Visual / UI bug 
Here's a visual/UI bug. [ATTACH SCREENSHOT]

What's wrong: [DESCRIBE what you see vs. what you expect]

Find the cause, fix it via the centralized config or the render layer (not by hardcoding), keep the fix incremental, then tell me exactly what you changed and which config value I can tweak to adjust it further.
PROMPT · Logic bug 
Here's a logic bug. Console output below. [PASTE the full console log from F12 → Console]

What happened: [DESCRIBE the wrong behavior]
What I expected: [DESCRIBE correct behavior]

Diagnose the root cause, add temporary debug logs if helpful, fix it incrementally, update the relevant test, and explain the fix in plain language.
PROMPT · Stuck — diagnose before fixing 
We've been stuck on this bug for a while. Don't patch blindly.

First, review the relevant code end-to-end and explain to me, in plain language, the full flow of how [FEATURE] is supposed to work. Then point to where the flow breaks. Wait for my confirmation before changing anything.

8Ship it — share a live link

For an HTML game this is easy. The agent writes the deploy workflow; you flip one setting in GitHub.

  • Have the AI prepare the GitHub Pages workflow and push it.
  • In GitHub → Settings → Pages, set Source to "GitHub Actions".
  • Confirm the live URL works on both desktop and a real phone.
  • Send the link to playtesters and collect feedback — the whole point of a prototype.
PROMPT · Set up auto-deploy to GitHub Pages 
Prepare this project for a GitHub Pages workflow that auto-publishes after every push to the main branch.

Do everything you can yourself (create the workflow file, set the correct build/base settings, commit, push). Then tell me exactly what I need to do on my side in the GitHub web UI, step by step.
Time budget

A small prototype is realistically 2–3 hours across 2–3 sessions (token limits reset on a rolling window). If you've proven the mechanic is fun, you're done — stop there. That was the goal.
